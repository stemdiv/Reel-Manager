R YouTube API Quota Estimator

Model how much YouTube Data API quota you'll need as the app grows. Since 1 June 2026 the quota is not one pool but four independent buckets, so there is no single number to request: each bucket saturates on its own schedule and is extended on its own line of the audit form. Set your assumptions on the left; the per-bucket projection, the binding constraint and the recommended request update live.

Quota model: YouTube Data API rules of 1 June 2026 (granular buckets) and 3 June 2026 (videos.batchGetStats), checked against the Quota Calculator and the API revision history on 20 September 2026. App-side implementation of record: QUOTA_LIMITS and YT_QUOTA_COSTS in youtube-playlist-manager.html.

How to read this

  • Four buckets, four ceilings. Since 1 June 2026: a pool of 10,000 units/day for every method except three, plus 100 search.list calls, 100 videos.insert calls and 10,000 batchGetStats calls, each in its own bucket. A search no longer costs 100 units — it costs one call out of a hundred. Raising the pool does nothing for search.
  • Two ceilings, measured in two different things. 100 search calls/day is the whole project's allowance, not each user's: two searches per active user caps you around 50 daily actives. The pool goes at the same time for an unrelated reason — writes cost 50 units each, so 6 edits per user is 300 units before a single read is served. At the Base preset both are already past their limit at month 0; the saturation chart says which is further past, and that is the one to argue first.
  • Effective = what you consume after cache; gross = worst case before it. Google evaluates worst case, so you request on gross + margin.
  • Request early, and per bucket. Audits take weeks to months. The June 2026 release notes state the granular buckets exist so increases can be verified and approved "based on specific method usage" — so the Audit and Quota Extension Form is argued bucket by bucket, each with its own use case. Request the level you need 6–12 months out.
  • Cheapest lever on search: cache result pages, lower the default maxResults (100 results = 2 calls, not 1), never fire on an empty or unchanged query. On the pool it is the reverse: writes at 50 units dominate, so batch and de-duplicate edits.
  • Calibrate, don't guess: the app's diagnostic log exports the four live counters. Feed the real ratios back into these sliders rather than trusting the defaults.
